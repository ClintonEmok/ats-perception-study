# Useful adaptive 3D interactions for ADA

## Objective

Make the standalone-capable STKDE 3D scene analytically interactive without turning it into a second timeline or a full voxel engine. Users should be able to recover how an interval was allocated, select a visible burst/cluster and focus its spatial-temporal context, and inspect a fixed real-clock-duration window moving through the adaptive axis before explicitly applying that window to the canonical dashboard timeline.

Purpose: The current scene already has the data needed for a useful interaction layer: epoch-bounded slices, crime counts, adaptive warp maps, volume profiles, burst volume samples, STKDE hotspots, and typed runtime callbacks. This task exposes those signals without hiding the clock-time meaning behind visual thickness or introducing dashboard-store coupling into the shared renderer.

Output: Pure allocation/scan helpers with focused tests, stable hotspot trajectory IDs, an interactive scene-runtime contract, clickable/hoverable slice/burst/trajectory primitives, dashboard synchronization callbacks, and standalone-safe inspector/scan behavior. No new dependency, voxel-volume engine, broad camera suite, page source-regression suite, or unrelated interaction system.

Established constraints and decisions:

- `Stkde3DScene` and its renderers are store-free; preserve that boundary. Dashboard state belongs in `Demo3dSpatialView`/the dashboard adapter, while `/stkde-3d` keeps local state.
- The adaptive axis is interval-based/piecewise-linear. Do not describe warped display duration as actual clock duration, and do not replace the existing `DurationVolumeProfileEntry.durationSeconds` meaning without an explicit compatibility decision.
- `useDashboardDemoFilterStore.selectedTimeRange` is epoch seconds. `useDashboardDemoTimeStore.timeRange` and `useDashboardDemoCoordinationStore.brushRange` are normalized ranges. Reuse `applyRangeToStoresContract` from `DemoDualTimeline` for commits so the timeline remains the sole temporal commit authority.
- `selectedBurstWindows`, `selectedHotspotId`, `activeSliceIndex`, `useSliceDomainStore.activeSliceId`, and the map's dashboard overrides are already the synchronization surfaces. Do not add a hidden second selected-time range to a store.
- `BurstVolumeModel` is derived from the selected dashboard burst and optional STKDE slice results. `HotspotTrajectoryOverlay` is optional data; when it is absent, the scene must still support slice selection and local focus.
- The existing source regression tests `src/app/stkde-3d/page.stkde.test.ts` and `src/app/dashboard-demo/page.shell.test.tsx` are intentionally deferred for this quick task. Use focused pure/synchronization tests, lint, typecheck, build, and manual smoke checks instead.

## Scope guardrails

- Keep this quick task to the 15 files listed in frontmatter. Do not modify page shell/source-regression tests; fold fixed-window assertions into the existing `src/app/stkde-3d/lib/volume-encoding.test.ts` and keep synchronization coverage in `syncDemo3dInteraction.test.ts`.
- Keep heavy computation out of the render path. Allocation metrics, trajectory ID preservation, and fixed-window arithmetic are pure O(number-of-slices) helpers; do not add a new worker or query endpoint.
- Keep hover state transient and local to the consumer. Only explicit selection/apply actions update canonical stores.
- Use actual epoch start/end values and existing `toDisplaySeconds`/`resolveEpochY` transforms. Never infer clock duration from mesh thickness, screen pixels, or adaptive Y distance alone.
- Dashboard commits must pass `fullTimeDomain` to `applyRangeToStoresContract` for epoch-to-normalized conversion even when `cubeScopeMode === 'brushed'`; `cubeTimeDomain` is display/filter scope only and must never become temporal commit authority.
- Do not add free-fly camera modes, voxelization, arbitrary cluster authoring, multi-burst comparison, or a second timeline implementation.
